# Deploying the FuturePath AI Backend (Free)

This guide takes the NestJS backend live on a free host. The frontend is deployed
separately on Cloudflare Pages (see `frontend/DEPLOY.md`).

## What the backend needs

| Dependency | Requirement | Free option |
|------------|-------------|-------------|
| Node runtime | Persistent process (SSE streaming — **not** serverless) | Render free web service |
| Database | MySQL / MariaDB | TiDB Cloud (free tier) or Aiven |
| Redis | **Optional** — off by default, in-memory fallback | Skip it |
| AI provider | `OPENCODEZEN_API_KEY` | Your existing key |

> **Why not serverless (Vercel/Netlify Functions)?** The chat uses Server-Sent
> Events, which need a long-lived process. Serverless functions time out, so we
> use a container/web-service host instead.

---

## Step 1 — Provision a free MySQL database

Render's own free database is PostgreSQL, but this app uses MySQL. Use a free
external MySQL provider:

### Option A: TiDB Cloud (recommended — generous free tier)
1. Sign up at <https://tidbcloud.com>.
2. Create a **Serverless** cluster (free).
3. Open **Connect** → copy the connection details (host, port `4000`, user, password).
4. Build your `DATABASE_URL`:
   ```
   mysql://<user>:<password>@<host>:4000/<dbname>
   ```
5. TiDB requires TLS, so you'll set `DATABASE_SSL=true` later.

### Option B: Aiven for MySQL
1. Sign up at <https://aiven.io>, create a free MySQL service.
2. Copy the Service URI (already in `mysql://…` form).
3. Aiven also requires TLS → `DATABASE_SSL=true`.

## Step 2 — Deploy to Render

The repo ships a `Dockerfile` and a `render.yaml` blueprint, so Render builds the
image, runs database migrations, and starts the API automatically.

1. Push your code to GitHub (already done).
2. Go to <https://dashboard.render.com> → **New** → **Blueprint**.
3. Connect the GitHub repo `FuturePathAI`. Render detects `render.yaml`.
4. It creates a service named **futurepath-api**. Before the first deploy, fill in
   the secret env vars (marked "sync: false") in the dashboard:

   | Variable | Value |
   |----------|-------|
   | `DATABASE_URL` | Your MySQL URL from Step 1 |
   | `DATABASE_SSL` | `true` (TiDB/Aiven need TLS) |
   | `CORS_ORIGINS` | Your Cloudflare Pages URL, e.g. `https://futurepath-ai.pages.dev` |
   | `OPENCODEZEN_API_KEY` | Your OpenCodeZen key |

   `JWT_SECRET` and `JWT_REFRESH_SECRET` are auto-generated by Render. The rest
   have sensible defaults from `render.yaml`.
5. Click **Apply** / **Deploy**. First build takes ~3–5 min.

On boot the container runs `prisma migrate deploy` (creating all tables) then
seeds two demo logins:
- `admin@futurepath.ai` / `admin123`
- `user@futurepath.ai` / `user123`

> **Change these credentials** before sharing the app publicly.

### Health check & docs
- Root: `https://futurepath-api.onrender.com/`
- Swagger: `https://futurepath-api.onrender.com/api/docs`

> **Free-tier cold starts:** Render free web services sleep after ~15 min idle.
> The first request after sleeping takes ~30–50 s to wake. Fine for a demo; for
> always-on, upgrade the plan or add an external pinger.

---

## Step 3 — Connect the frontend

In the Cloudflare Pages project settings, set:
```
VITE_API_BASE_URL=https://futurepath-api.onrender.com
```
Then redeploy the frontend. Also make sure the backend's `CORS_ORIGINS` includes
the exact Pages URL (scheme + host, no trailing slash).

## Deploying elsewhere

The `Dockerfile` is host-agnostic. On **Railway** or **Fly.io**: point the platform
at the repo/Dockerfile and set the same env vars. Railway also offers a one-click
MySQL plugin — use its provided `DATABASE_URL` and set `DATABASE_SSL=false` if it's
an internal (non-TLS) connection.

## Local production test

```bash
npm ci
npm run build
npx prisma migrate deploy   # against your DATABASE_URL
npm run start:prod
```

## Troubleshooting

- **CORS errors in browser:** `CORS_ORIGINS` must exactly match the frontend
  origin (`https://…`, no trailing slash). Multiple origins are comma-separated.
- **DB connection refused / TLS required:** set `DATABASE_SSL=true`. If the
  provider uses a self-signed cert, set `DATABASE_SSL_INSECURE=true` (less secure).
- **Migrations didn't run:** check the deploy logs — `prisma migrate deploy` runs
  as the container's start command before `node dist/main`.
- **502 right after deploy:** likely still waking from cold start or mid-migration;
  wait ~1 min and retry.
